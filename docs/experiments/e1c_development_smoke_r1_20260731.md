# E1c 开发集真实 API 冒烟测试 R1

## 1. 结论

E1c 六条件端到端运行器已经通过真实 DeepSeek API 连通性检查：

- 9 道开发题、6 个条件，共 54 个条件单元全部完成；
- 73 次供应商请求全部一次成功；
- 无重试、无解析失败、无工具执行失败；
- 任务、提示词、运行配置、运行器、评分器、工具 Schema、逐条记录和汇总报告均已快照并写入 SHA-256 manifest；
- 36 道 `end_to_end_evaluation` 任务未被读取或运行。

冒烟测试同时发现了一个需要保留到正式实验中的关键现象：

> 在不暴露工具 Schema 的独立边界门控中，模型正确拒绝了 8 道无需调用的任务；一旦同时暴露工具 Schema，即使提供相同的冻结边界规则，模型仍对这 8 道任务全部调用了工具。

因此，本轮结果支持继续完成开发集实验，但不允许据此进行确认性推断，也不应立即解封正式评测集。

## 5. 损失分解

### 5.1 最终答案正确率不足以评价系统可靠性

六个条件的最终答案正确率均为 100%，但其调用行为明显不同：

- `direct_fc` 和 `boundary_guided_fc` 均存在 8/8 的过度调用；
- `model_gate_oracle_parameters` 在唯一必须调用题上发生 1/1 的工具绕过；
- 工具选择、参数生成和执行在本轮可评估单元中均正确。

如果只报告最终答案正确率，工具绕过和过度调用会被完全掩盖。E1c 必须继续分别报告：

- 边界正确性；
- 工具选择正确性；
- 参数正确性；
- 工具执行状态；
- 最终答案正确性；
- `primary_failure_stage`。

### 5.2 Schema 暴露是当前最可能的过度调用来源

运行器对两个自主函数调用条件均使用 `tool_choice=auto`，模型拥有直接回答的能力，工具描述中也没有“必须调用”的指令。

观察到：

- 不暴露工具 Schema、先单独进行边界判断：8 道无需调用题全部不调用；
- 暴露相同 5 个工具 Schema：8 道无需调用题全部调用；
- 在 Schema 暴露条件中追加冻结边界规则，没有改变调用行为。

在本轮设计范围内，这说明 Schema 暴露形成了强工具可供性偏置。该结论仍是开发集诊断，不是正式因果结论。

### 5.3 严格版本题复现了工具绕过

唯一 A003 任务要求按冻结版本常数和窄容差计算。独立边界门控却选择直接回答，并恰好给出正确数值。

这仍应计为 `boundary_decision_error`，因为系统没有形成可追溯的版本化计算证据。该例说明：

> “模型知道答案”不等于“模型满足了证据要求”。

## 6. 工程验收

本轮可以通过以下冒烟门槛：

- API 鉴权与 OpenAI-compatible 请求格式有效；
- 工具 Schema 可被供应商接受；
- `tool_choice=auto` 的直接回答和函数调用响应均可解析；
- 五工具注册和本地执行链有效；
- 工具结果可回填模型并得到结构化最终答案；
- 六条件记录字段和失败阶段归因可生成；
- 运行产物 manifest 可用于后续哈希复核。

未发现需要修改冻结运行器、提示词或策略的实现错误。

## 7. 限制与下一步

本轮只有 8 道 `ANSWER_WITHOUT_TOOL` 和 1 道 `CALL_VERIFIED_TOOL`，不能据此比较方法总体性能。下一步应：

1. 保持 E1b 冻结策略 v1、E1c 提示词 v1 和运行器 v1 不变；
2. 对完整 24 道 `runner_development` 运行六条件实验；
3. 检查五个工具家族、6 个必须调用任务和 18 个无需调用任务；
4. 至少完成预注册重复次数所需的开发运行，确认波动、重试和失败归因；
5. 只在开发运行未发现实现缺陷后，形成是否解封 36 道正式评测集的书面决策；
6. 正式评测集在解封前不得用于修改提示词、边界策略、评分器或任务构造。

本冒烟结果仅证明“实验链路可执行”并提供开发诊断，`confirmatory_inference_allowed` 继续保持 `false`。
