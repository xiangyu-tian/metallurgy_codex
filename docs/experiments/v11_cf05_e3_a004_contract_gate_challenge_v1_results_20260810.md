# CF-05 E3：A004 契约门控边界挑战 v1 结果

## 1. 结论

A004 单调用结构门与契约裁决候选完成 15 条开发性离线边界挑战：

| 指标 | 结果 |
| --- | ---: |
| 挑战案例 | 15 |
| 通过 | 15 |
| 失败 | 0 |
| 外部 API 调用 | 0 |
| 冶金工具执行 | 0 |
| 决策阶段读取预期答案 | 否 |

本轮证明候选规则能够保守处理已知边界，但挑战集由开发者在机制形成后构造，因此不属于独立模型验证，不能用于确认性推断，CF-05 仍为 `in_progress`。

## 2. 覆盖范围

挑战集覆盖：

- 正确的 A004 单调用；
- 零调用；
- 未登记工具；
- 无效参数 JSON；
- 参数映射缺失；
- 总和归一化与 L2 归一化错配；
- 语义可能匹配但无正式执行资格的候选工具；
- 三个已登记工具中的唯一契约裁决；
- 两次完全相同的 A004 调用；
- 同名 A004 中一次参数错误、一次参数正确；
- 所有候选均不兼容；
- 一个有效 A004 与未知或不可解析调用并存；
- 通用 A004 契约对元素标签输入的兼容性。

预期结果存放在挑战文件的 `expected` 区域，但运行器先只提取 `input.problem_text` 和 `input.raw_response` 完成裁决，之后才读取预期结果进行离线评分。

## 3. 本轮实现加固

### 3.1 同名调用参数按索引绑定

原实现通过工具编号回找被选调用的参数。如果同一个工具出现两次，且第一次参数错误、第二次参数正确，可能错误取回第一次参数。

现改为：每个候选评价保留 `call_index`，最终参数直接取自唯一兼容评价对应的原始调用索引。挑战案例 `CG-011` 验证所选参数为完整的 `{"x": 2.0, "y": 3.0}` 映射。

### 3.2 不完整候选证据强制复核

当多调用中包含未登记工具或不可解析的参数 JSON 时，即使另一个 A004 看似唯一兼容，也不能证明未知调用不适用。

现将以下情况标记为 `unresolved_candidate_evidence=true`，并强制：

```text
decision = review_required
decision_reason = candidate_evidence_incomplete
```

这避免门控在信息不完整时扩大自动执行权限。

### 3.3 契约加载与评分输入分离

新增的挑战运行器只加载三份契约来源，完全不加载任务金标或离线评分表。原 144 条回放仍在单独路径中执行，验证结果保持：

- 3/3 多调用被阻断并唯一裁决为 A004；
- 141 个原始单调用零误阻断；
- 门控后开发集回放为 144/144。

## 4. 证据边界

15/15 不能被解释为真实模型泛化准确率，原因包括：

1. 案例由开发者根据当前规则构造；
2. 只覆盖 A004、E3C005、E3C027 三个契约画像；
3. 未使用未见任务或新模型响应；
4. 未执行真实工具，未验证计算结果正确性；
5. 未改变原始三次多调用错误的统计记录。

## 5. 下一步

下一步应生成一个“后置评测开启包”，在提交哈希固定后再使用未见输入验证：

- 开启包只包含冻结请求、Schema、门控配置和评分程序；
- 先提交并推送，再决定是否授权外部 API；
- 运行时每个单元只尝试一次，不自动重试，不执行冶金工具；
- 原始模型选择结果和门控后结果分别保存，禁止用门控覆盖模型错误；
- 结果仍属于开发性评测，不进入 H3/H4 确认性数据。
