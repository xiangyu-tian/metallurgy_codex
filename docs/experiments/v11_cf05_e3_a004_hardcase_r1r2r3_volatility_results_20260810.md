## 稳定失败的精确复现

失败单元三次均为：

```text
task = E1B2-A004-008
condition = contract_mismatch-4
tool_pool_size = 120
method = dense_top5
```

三次响应均按相同顺序返回：

```text
A004
E3C005
E3C027
```

即三轮工具调用数量均为3，工具序列也完全一致。虽然提示词明确要求`exactly one native function call`，模型仍把三个具有归一化含义、且参数表面兼容的工具共同调用。

这说明错误不是“未找到A004”，而是：

> 候选检索已召回正确工具，但模型没有在单位和归一化、pymatgen分数归一化与L2向量归一化之间完成单一契约裁决。

## 对项目主线的意义

该错误同时触及项目的三个核心问题：

1. 模型知道需要调用工具，没有绕过计算；
2. 模型知道A004适用，但没有排除相似工具；
3. 系统若直接执行响应，会一次触发三个不同归一化语义的工具，缺少调用数量和契约一致性保护。

因此，结果支持继续开发两层防护：

```text
第一层：确定性调用结构门
检测 tool_call_count != 1
→ 禁止进入工具执行阶段

第二层：契约语义裁决
在多个候选工具之间比较
用户要求的归一化基准、输入语义、输出语义和适用域
→ 只允许一个工具晋级，或转为 review_required
```

第一层能够立即防止错误执行，但本身不能提高原始工具选择准确率；第二层才用于解决“多个相关工具中究竟选哪个”。
