# E1c 完整开发集 R1 结果

## 1. 总体判断

E1c 完整开发集六条件实验已经成功完成：

- 24 道 `runner_development` 任务；
- 6 个冻结条件；
- 144 个条件单元；
- 198 次供应商请求；
- 0 次重试、0 次解析失败、0 次工具执行失败；
- 8 个正式运行产物的 SHA-256 全部与 manifest 一致；
- 36 道 `end_to_end_evaluation` 任务仍未打开。

本轮没有发现需要修改冻结提示词、运行器、工具 Schema 或评分器的通用实现错误。开发配置规定 `development_repeats=1`，因此本轮已经完成 E1c v1 的开发运行要求。

主要研究性发现是：

> 独立边界门控与自主函数调用呈现方向相反的偏差。独立门控从不调用工具，导致 6/6 必须调用任务被绕过；一旦暴露工具 Schema，自主函数调用又变成 24/24 全部调用，导致 18/18 无需调用任务被过度调用。冻结边界提示没有抵消 Schema 暴露造成的调用诱导。

## 4. 边界损失

### 4.1 独立模型门控：完全不调用

`model_gate_oracle_parameters` 的结果为：

- 调用数：0/24；
- 无需调用任务正确拒绝：18/18；
- 必须调用任务绕过：6/6；
- 边界正确率：18/24，75%；
- Bypass Rate：100%；
- Overcall Rate：0%。

6 个必须调用任务包括：

- 4 个冻结版本、窄容差的 A003 摩尔质量任务；
- 2 个高动态范围、六位小数的 A004 归一化任务。

模型在 6 题上均绕过工具，其中 5 题仍直接给出了正确答案，只有 `E1C-A003-005` 最终数值错误。

这说明必须把“是否形成规定的外部计算证据”与“答案是否碰巧正确”分开：

> 无工具答案正确，不会自动消除严格版本、窄容差任务的证据要求。

### 4.2 自主函数调用：完全调用

`direct_fc` 与 `boundary_guided_fc` 均为：

- 调用数：24/24；
- 必须调用任务召回：6/6；
- 无需调用任务过度调用：18/18；
- 边界正确率：6/24，25%；
- Bypass Rate：0%；
- Overcall Rate：100%。

两个条件使用相同 5 个 Schema、相同工具顺序、模型、温度和任务，唯一差异是后者加入冻结边界提示。结果完全相同，表明单纯增加边界文字未能改变该模型在 Schema 暴露下的调用倾向。

这不是运行器强制调用：

- 请求使用 `tool_choice=auto`；
- 模型可以返回普通文本答案；
- 工具描述中没有“必须调用”；
- 不暴露 Schema 的边界门控能够正常直接回答。

因此，开发结果把“Schema 暴露造成的工具可供性偏置”确定为后置实验需要验证的核心机制之一。

## 5. 工具选择与参数损失

### 5.1 工具选择

自主函数调用的 48 个调用单元中：

- `direct_fc`：24/24 选择正确；
- `boundary_guided_fc`：24/24 选择正确。

在只有 5 个工具、且任务工具家族区分清晰的当前实验中，工具错选尚不是主要损失来源。本结果不能外推到 120 工具或高相似近邻条件。

### 5.2 参数生成

`oracle_gate_model_parameters` 在 6 个必须调用任务中：

- 参数 JSON 均可解析；
- 6/6 工具执行成功；
- 4/6 与预注册参数完全一致；
- 6/6 最终答案正确。

两个非完全匹配均来自 A004：

- 预注册输入是原始高动态范围组分；
- 模型先自行归一化，再把等比例组分传给归一化工具；
- 参数不再与原始输入完全一致，但由于 A004 对等比例缩放不变，工具输出仍正确。

`boundary_guided_fc` 的两个参数非完全匹配来自 B019：

- 模型在预注册参数之外增加了 Schema 默认字段 `component="B"`；
- 工具执行和最终答案均正确；
- 由于冻结指标要求完整 JSON 集合相等，仍记为非完全匹配。

这些结果说明同时保留以下指标是必要的：

- 参数 JSON 有效性；
- Exact Parameter Match；
- 工具执行成功率；
- 最终答案正确率。

不建议在看到开发结果后放宽 Exact Parameter Match，否则会形成结果驱动的评分修改。语义等价参数可作为后续探索性指标，但不能替代冻结主指标。

## 6. 最终答案与失败阶段

六条件中只有 1 个最终答案错误：

| 任务 | 条件 | 冻结动作 | 模型动作 | 结果 |
|---|---|---|---|---|
| `E1C-A003-005` | `model_gate_oracle_parameters` | 调用工具 | 直接回答 | 摩尔质量不满足参考值 |

尽管如此，最终正确率仍然无法区分系统行为：

- `no_tool`：100%；
- `forced_verified_oracle_parameters`：100%；
- `direct_fc`：100%，但 18 次过度调用；
- `boundary_guided_fc`：100%，但 18 次过度调用；
- `model_gate_oracle_parameters`：95.8%，同时存在 6 次工具绕过。

这进一步证明 E1c 的损失分解设计是必要的。正式报告不能只用 End-to-End Accuracy 评价工具协同可靠性。

## 7. 是否需要修改冻结实现

当前判断：不需要。

已验证：

- 六条件均能通过真实 API 执行；
- 普通文本、动作 JSON、参数 JSON 和函数调用均能解析；
- 工具选择、工具执行、结果回填和最终评分链完整；
- 错误阶段优先级能够把“答案正确但行为错误”记录为边界或参数错误；
- 严格参数匹配的结果与协议定义一致；
- 无请求失败和重试异常；
- 运行报告与 manifest 完整。

观察到的全不调用、全调用和参数非完全匹配属于需要测量的模型行为，而不是通用实现错误。不得使用开发结果修改 E1b 策略 v1。

## 8. 后置评测开启建议

E1c v1 已满足“开发运行完成且无通用实现缺陷”的技术条件，可以进入后置评测开启准备，但还不能直接运行后置集。

开启前应新增并冻结：

1. 评测集开启记录，绑定开发结果 run ID、Git commit 和 manifest 哈希；
2. 只包含 36 道 `end_to_end_evaluation` 任务的不可变快照；
3. `run_config_evaluation_v1.json`，固定模型、温度、条件顺序和重复数；
4. 适用于评测状态的运行器报告字段，不能继续写成 `evaluation_split_opened=false`；
5. 评测产物 manifest 和“不允许依据评测结果修改 v1”的约束；
6. 用户对向外部模型发送 36 道后置任务的单独授权。

完成上述冻结后，才能运行后置评测。E1c 后置评测仍是机制实验，不会把 CF-01 至 CF-11 自动标记为通过，也不会使 `Core Frozen=true`。
